Wardian

Where local agent work becomes visible, durable, and malleable.

Run the CLI agents you already use in real workspaces. Keep their sessions and evidence visible, then turn successful work into reusable prompts, skills, classes, workflows, and project context.

01 Graph

Agents that know about each other

The Graph draws the agents and the links between them. Edges come from a team you create, a link you make by hand, or a shared workspace, and you can ignore the ones you do not want.

The topology is written to topology.json, so an agent can read its own neighbours before it sends anything.

Graph guide

02 Ask and reply

Handoffs that leave a record

An ask carries a durable id. The reply comes back against that id with a status and any choices the ask offered, and both ends land in the Inbox.

A message can queue while the receiving agent is busy or offline, and it keeps its delivery receipt either way.

Inbox guide

03 Two interfaces

A GUI for you, a CLI for your agents

You get a desktop app. Your agents get wardian, the same control surface as a command line: list peers, send a task, wait for the reply, read the result.

An agent can spawn a peer, ask it a question and block on the answer without a person relaying messages between two terminals.

Wardian CLI guide
an agent, using wardian 
$ wardian agent list
NAME            CLASS     STATUS
Docs-Codex      Coder     processing
Docs-Reviewer   Reviewer  idle
$ wardian ask Docs-Reviewer "does the capture manifest look right?"
waiting for reply...
reply    No blocking findings. Sizes are within budget.
$ wardian agent spawn --class Coder --name Docs-Encoder
spawned  Docs-Encoder  class=Coder
$ wardian memory save "Clips render near 1200px, so capture at 1280" \
    --evidence "a 1600px capture was shown at 0.4x and text turned to mush"
saved    id=7c1f9ab2  scope=workspace  revision=1

04 Workflows

Workflows that branch, loop, and wait

Build a run as a node graph: agent calls, commands, scripts, files, memory, branches, loops, and waits. The workflow owns the control flow, so a branch is decided by the run itself.

Input parameters and shared storage pass values between nodes, and the builder validates the graph before it executes.

Automations guide

05 Dashboard

The fleet, not the tab

One row per agent: state, active time, turns, tokens, files touched, and lines changed, with a provider strip across the top.

Pick the window and the trend is computed over it.

Dashboard guide

06 Files on disk

Everything is a file you can read

Prompts, classes, skills, workflows, results, and topology are files. The Library and the Explorer show the same directory you can open in any editor.

The app is a view onto that directory, so the state stays readable when the app is closed.

Explorer guide

07 Memory

Memory that carries its evidence

Every saved memory stores the excerpt it came from. Records are scoped to an agent or a workspace, and an update keeps the previous revision rather than overwriting it.

Agent memory is opt-in under Settings, and inside a managed terminal an agent can only reach its own records.

08 Classes

Roles you define once

A Class is a role: instructions, skills, and prompts that every agent of that role receives when it starts.

The definition is a Library entry on disk, so editing the class changes the next agent that uses it.

Class management guide
